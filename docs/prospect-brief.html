TestOps Intelligence Agent — Prospect Brief

Prepared by Trinh Nguyen (Martin) for AITOMATIC Round 3, 17 Nov 2026 · Proof of concept on synthetic data · Repo: {{GITHUB_URL}} · Demo: {{LIVE_DEMO_URL}}

Prospect

Kestrel Commerce (fictional). Mid-sized B2B commerce SaaS: 4 services (checkout-web, payments-api, inventory-svc, support-assistant with scored LLM evals), 6 CI pipelines, 120 runs and 892 test attempts in the 30-day window ending 2026-11-13. Releases are approved by a release manager from the CI status page.

Problem

Each run is described by three sources that disagree: a CI summary webhook, runner attempt events, and artifact logs. They use different timestamp formats (ISO with offset, epoch seconds, epoch milliseconds, naive strings), different status words (PASS, passed, SUCCESS), and redeliver events. Engineers triage failed runs by hand, infrastructure failures get blamed on tests, and a summary can say PASS while a gating test never reported a result. Release decisions are slow or rest on a rollup nobody can audit.

Why this prospect and problem

I spent 2.5 years building cloud test execution (session lifecycle, retries, provisioning, artifacts) and six months on agentic testing features. I know these failure modes from the inside and can defend every rule in the knowledge file. No employer data is used: the dataset is generated by a seeded script in the repository.

Personas

VP Engineering (budget owner)

Wants fewer engineer-hours lost to triage, faster and safer release decisions, and a bounded pilot with a clear exit. Fears hallucinated release advice, an ROI nobody can verify, a long security review, and vendor lock-in.

Principal Engineer / QA Platform Lead (technical evaluator)

Owns the CI data and the team's trust. Wants provenance for every number, a deterministic release gate, read-only access, no model-generated SQL, and a credible path from synthetic data to the real CI feed. Fears a model deciding releases, prompt injection through logs, and another dashboard to maintain.

Principal objections

  1. The model will hallucinate a root cause or approve a bad release. Verdicts come only from a tested policy function; the model cannot write one. A validator rejects unknown record ids, ungrounded numbers and stray verdicts, and sends the draft back once.
  2. Where do the ROI numbers come from? From the pilot's week-1 baseline. Today there is a formula and a sensitivity table, nothing more.
  3. We cannot send CI logs to a cloud model. The model endpoint is any OpenAI-compatible URL, logs are treated as untrusted data, and the pilot runs on the customer's account.
  4. Our CI already retries. It retries; it does not separate infrastructure from product failure, or expire a quarantine.
  5. Why not a dashboard? The rules could be SQL. The value is a cited answer to an arbitrary question, plus a rule file that records your leads' judgment.

Proposed pilot (4 weeks, illustrative)

Read-only token, one CI source, one service, human-in-the-loop. W1 ingest, data-quality report, measured triage baseline. W2–3 shadow mode: the agent triages every failed run; engineers accept or override in one click. W4 measurement, rule tuning, go/no-go. Success criteria, targets fixed in W1 against the baseline: evidence-backed classification accepted without edit (starting target 70% of failed runs); median time-to-first-classification reduced (starting target 30%); zero SHIP recommendations on runs a human later held; zero evidence ids that fail to resolve; at least one integration defect surfaced by the data-quality report.

Assumptions

Synthetic data stands in for a real feed (2,053 raw events, 2,051 unique). Triage minutes (10/20/35) and loaded rates ($40/60/90 per hour) are assumptions in the rule file, not measurements. Naive artifact timestamps are UTC per source contract. The critical suite is the gating suite.

Limitations

Synthetic data, one tenant, no SSO. Live model latency measured during development at roughly 18–48 s per question on a free tier; not an SLA. "Proven" flakiness requires same-commit reruns; root causes are hypotheses because diffs are not in the data. The rule file is hand-authored, not learned. Replay traces and the public demo URL are being finalised before the meeting.
