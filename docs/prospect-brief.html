01Prospect

Kestrel Commerce (fictional): a mid-sized B2B commerce SaaS. Four services: checkout-web, payments-api, inventory-svc, and support-assistant, which has scored LLM evals. Six CI pipelines, 120 runs and 892 test attempts in the 30 days to 13 Nov 2026. A release manager approves releases from the CI status page.

02Problem

Three sources describe every run, and they disagree:

  • the CI summary webhook;
  • the runner's attempt events;
  • the artifact logs.

They mix timestamp formats (ISO with offset, epoch s and ms, naive) and status words (PASS, passed, SUCCESS), and they redeliver events. Engineers triage failed runs by hand. Grid failures get blamed on tests. A summary can say PASS while a gating test never reported a result. Release decisions are slow, or rest on a rollup nobody can audit.

03Why this problem

Two and a half years building cloud test execution for an enterprise test-automation platform (sessions, retries, provisioning, artifacts), then six months on agentic testing features. The rule file encodes those failure modes. No employer data is used; the dataset comes from a seeded generator in the repository.

06Principal objections and answers

“It will hallucinate a root cause or approve a bad release.”Verdicts come only from a tested policy function (rules R1–R6). A validator rejects unknown ids, ungrounded numbers and stray verdicts.
“Where do the ROI numbers come from?”From the pilot’s week-1 baseline. Today there is a formula and a sensitivity table, not a promised figure.
“We cannot send CI logs to a cloud model.”It works with any OpenAI-compatible endpoint. Logs are handled as untrusted data. The pilot runs in the customer’s account.
“Our CI already retries.”Retries do not separate infrastructure failures from product failures. Every failure here carries a defect type: Product Bug, Automation Bug, System Issue or To Investigate.
“How do we know the agent itself is reliable?”Golden, adversarial and robustness evals run repeatedly and are reported as pass rates across repeated runs. A run that falls back to the offline planner is not counted as a model pass.

07Proposed pilot · 4 weeks, illustrative

Scope: read-only token, one CI source, one service, human-in-the-loop.

W1
Baseline
Ingest, a data-quality report, measured triage time.
W2–3
Shadow mode
The agent triages every failed run; engineers accept or override.
W4
Decide
Measure, tune the rules, go/no-go.

Success criteria. Targets are fixed in W1 against the baseline:

  • classifications accepted without edit: start at a 70% target;
  • median time to first classification: down 30%;
  • zero SHIP recommendations on runs a person later held;
  • zero evidence ids that fail to resolve;
  • at least one integration defect found by the data-quality report.

08Assumptions and limitations

Assumptions. Triage minutes (10 / 20 / 35) and loaded rates ($40 / 60 / 90 per hour) are rule-file assumptions, not measurements. Naive artifact timestamps are UTC by source contract. The critical suite gates releases.

Limitations. One tenant, no SSO. Live latency was measured on a free model tier (8–14 s typical) and is not an SLA. Wording varies between runs; the eval harness measures how much. “Proven” flakiness needs same-commit reruns. Root causes are hypotheses, because code diffs are not in the data.
