# TestOps Intelligence Agent — Prospect Brief

Trinh Nguyen (Martin), AITOMATIC Round 3, 17 Nov 2026. Proof of concept on synthetic data. Repo: {{GITHUB_URL}} · Demo: {{LIVE_DEMO_URL}}

## Prospect

**Kestrel Commerce** (fictional). Mid-sized B2B commerce SaaS: 4 services (`checkout-web`, `payments-api`, `inventory-svc`, `support-assistant` with scored LLM evals), 6 CI pipelines, 120 runs and 892 test attempts in the 30 days to 2026-11-13. A release manager approves releases from the CI status page.

## Problem

Three sources describe each run and disagree: a CI summary webhook, runner attempt events, and artifact logs. Timestamps come as ISO with offset, epoch seconds, epoch milliseconds and naive strings; status words are `PASS`, `passed`, `SUCCESS`; events are redelivered. Engineers triage failed runs by hand, grid failures get blamed on tests, and a summary can say PASS while a gating test never reported a result. Release decisions are slow or rest on a rollup nobody can audit.

## Why this problem

2.5 years building cloud test execution (sessions, retries, provisioning, artifacts) and six months on agentic testing features. I know these failure modes from the inside and wrote the rule file from that experience. No employer data: the dataset is generated by a seeded script in the repository.

## Personas

**VP Engineering (budget owner).** Wants fewer engineer-hours lost to triage, safer release decisions, and a bounded pilot with a clear exit. Fears hallucinated release advice, unverifiable ROI, a long security review, lock-in.

**Principal Engineer / QA Platform Lead (technical evaluator).** Owns the CI data and the team's trust. Wants provenance for every number, a deterministic gate, read-only access, no model-written SQL, and a path from synthetic data to the real feed. Fears a model deciding releases, prompt injection through logs, another dashboard to maintain.

## Principal objections

1. *It will hallucinate a root cause or approve a bad release.* Verdicts come only from a tested policy function; a validator rejects unknown ids, ungrounded numbers and stray verdicts.
2. *Where do the ROI numbers come from?* From the pilot's week-1 baseline. Today: a formula and a sensitivity table.
3. *We cannot send CI logs to a cloud model.* Any OpenAI-compatible endpoint; logs are untrusted data; the pilot runs in the customer's account.
4. *Our CI already retries.* It does not separate infrastructure from product failure, or expire a quarantine.
5. *Why not a dashboard?* The value is a cited answer to an arbitrary question, plus a rule file that records your leads' judgment.

## Proposed pilot (4 weeks, illustrative)

Read-only token, one CI source, one service, human-in-the-loop. **W1** ingest, data-quality report, measured triage baseline. **W2–3** shadow mode: the agent triages every failed run; engineers accept or override in one click. **W4** measurement, rule tuning, go/no-go. Success criteria, targets fixed in W1 against the baseline: classification accepted without edit (starting target 70% of failed runs); median time-to-first-classification down (starting target 30%); zero SHIP recommendations on runs a human later held; zero evidence ids that fail to resolve; at least one integration defect found by the data-quality report.

## Assumptions

Synthetic data stands in for a real feed (2,053 raw events, 2,051 unique). Triage minutes (10/20/35) and loaded rates ($40/60/90 per hour) are assumptions in the rule file, not measurements. Naive artifact timestamps are UTC per source contract. The `critical` suite is the gating suite.

## Limitations

Synthetic data, one tenant, no SSO. Live model latency measured during development at 18–48 s per question on a free tier; not an SLA. "Proven" flakiness needs same-commit reruns; root causes are hypotheses because diffs are not in the data. The rule file is hand-authored. Replay traces and the public demo URL are being finalised before the meeting.
